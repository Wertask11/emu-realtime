# マイCityの部屋：実装と運用

2026年11月21日 JST。設計PR #381に対するオーナーの「いいよ」は実装承認として記録する。マージ・本番公開の承認とは扱わない。本番データ・台帳・商品・Rules・環境設定は変更していない。

## 実装した操作

1. SchoolPark City → MY CITY「自分の部屋」を開く。既存の3D店舗からの入口も同じ。
2. 最初から無料の机・椅子・冷蔵庫くんが置かれる。部屋を開くだけでは部屋文書を作らない。
3. 道具を選んでドラッグ、矢印ボタン、キーボードで動かす。「向きを変える」「持ち物へ戻す」も使える。
4. 持ち物の道具を押すと空いている場所へ置く。壁飾りは左右の壁を切り替えられる。壁紙・床・窓は各1枠。
5. 「配置を保存する」。通信失敗時は配置と同じrequestIdを画面に残し、同じ内容で再送できる。409時には自動上書きせず、確認して読み直す。
6. 初期状態は非公開。「公開の確認へ」→説明とチェック→「確認して公開する」で公開する。
7. 「画像とURLをシェア」で画像と公開URLを確認してから端末の共有画面へ進む。非対応端末はPNG保存・URLコピー・Xの投稿画面を使用する。Xへの画像添付と投稿は本人操作。
8. 公開ページは匿名で部屋だけを閲覧可能。いいね・通報は既存のログインとSchoolPark Cityの入場条件を確認してから受け付ける。独自ログインは追加していない。
9. 非公開にすると古い公開URLを無効化。再公開時は別の乱数URLとなる。運営の公開停止は本人の保存・非公開/再公開では解除できない。

旧MY CITYの実績一覧は表示しない。チェックイン・Quest・星・Guildの記録と既存APIは削除していない。体験スポットにはPassport・星空への導線を残す。

## データとAPI

既存Firebase認証と、サーバー管理の`sp_auth_links`・有効なSchoolPark IDを使用する。Cityの入場条件を再利用し、冷蔵庫くんのPlus/Pro制限は持ち込まない。公式ショップの交換プラン・回数・料金は変更しない。

| API | 動作 |
|---|---|
| GET `/api/schoolpark/city/room/me` | 本人の配置と、引渡し済みの公式ショップ注文から計算する持ち物 |
| PUT `/api/schoolpark/city/room/me` | `{requestId,expectedRevision,visibility,layout}`。範囲・重なり・個数・所有・最新版をサーバーで検証 |
| GET `/api/schoolpark/city/room/:publicId` | 匿名可。部屋と使用中の道具定義だけ。SchoolPark ID・UID・注文ID・通報者を返さない |
| POST `…/:publicId/like` | 認証必須。同じSchoolPark IDは1回。自分の部屋は不可 |
| POST `…/:publicId/report` | 認証必須。定型理由だけ。同じ公開URLへの重複通報は加算しない |
| GET `…/admin/reports` | 既存requireOwner＋最新の運営アドレス確認。最大20件。時刻と文書パスのカーソルで同時刻の通報を落とさない |
| POST `…/admin/moderation` | 運営だけが公開停止・確認後の再公開を行う |

`server.js`への追加は1行。匿名公開GETを既存City全体の認証middlewareに遮られないよう、部屋ルーターを先にmountする。

- `city_rooms/{SchoolPark ID}`：schemaVersion、配置、revision、公開状態、内部の使用注文証跡、集計、作成/更新/運営確認時刻。
- `city_rooms/_public/ids/{publicId}`：内部のSchoolPark ID対応とactiveフラグ。publicIdは暗号学的乱数128bit・base64url22文字。
- 部屋配下の`likes`、`city_room_reports`、`city_room_requests`。自由記述・ユーザー投稿・名前は保存しない。
- Firestore Rulesへの追加はserver-onlyの新しいmatchブロック1つ。直接SDK読書きは本人・第三者・運営とも拒否。既存の星空ブロックを保持。
- 部屋と公開IDの履歴は自動削除しない。非公開化で公開URLだけを無効にする。既存アカウント削除方針へ組み込む場合は、この新コレクションと子文書を削除対象として運営確認する。
- 保存再送の受領記録は7日を過ぎたものを、次回の明示保存時に最大4件ずつ削除する。これは物理的な7日TTL削除を保証するものではない。TTL設定・削除ジョブは作成していない。

## 持ち物の境界と商品登録の残件

有料10種のID・表現・サイズは`backend/city-room-items.json`。ショップ担当への登録用一覧は[商品連携.json](商品連携.json)。価格はここに持たない。価格案10〜20 EMUERは[提案](提案.md)の一覧であり、本番価格の決定ではない。

取得元は`mitemiru_orders`の本人Passportに一致する文書。`fulfilled`、`schoolpark-official`、`schoolpark_virtual`、カタログで定義した`room-…`をすべて確認する。無料3種以外を自己申告・paid・他店舗・他人の注文から追加しない。置いた有料道具の注文は保存transaction内でも再確認する。返却などで注文が無効になれば、次回本人/公開閲覧時に表示から外す。原本注文や保存済み配置を勝手に消さない。

現在の共通デジタル配布カタログには部屋用IDがない。`mitemiru.cleanProduct`は登録済みの配布ファイルを必要とする。このPRは保護対象のmitemiru・private-assets/catalogを変更しないため、**「交換用10商品が本番購入可能」とは判定しない**。ショップ担当側で次を行う必要がある。

1. 配布用ファイルとカタログに、このPRの10個の正確なIDを登録する。価格・在庫・締切・回数・配布条件はオーナーが既存運営画面で決める。
2. 公式ショップのデジタル商品として下書き登録し、内容を確認して販売する。
3. 現行デジタルダウンロードは注文を自動でfulfilledにしない。既存の運営引渡し処理でfulfilledを記録してから部屋に入る。即時自動引渡しを希望する場合は、ショップ担当の別変更として審査する。
4. 本番交換試験は別途承認後。今回、実EMUERの消費・付与・返却は0。

## 読み取り負荷と障害時

定期ポーリング、onSnapshot、公開部屋の一覧・ランキング、全件スキャンはない。無関係なCity再描画で部屋の読み込みや未保存配置をやり直さない。並行reloadを抑止し、アカウント切替時は保留リクエストをabortして表示とメモリーを消去する。

- 匿名公開GET：対応文書1＋部屋1＋使用有料注文0〜24。通常2、最大26文書。使っていない全注文を読まない。
- 本人GET：最新アカウント1、SchoolPark IDリンク1、本人ID1、部屋1、対象注文query1回（最大65文書）。有料所有64件までを処理し、65件検出時は切り捨てず409で停止。query0件でもFirestore最少課金readがある。既存認証のcold-cache処理は別途発生する。
- 公開開始後/運営は、既存入場ポリシーで入場可と判定できれば公式パスの追加探索をしない。公開前の入場条件では既存パス判定を使用する。
- 保存：上記の本人確認＋所有queryに加え、room/requestのtransaction読取り、有料証跡最大24、公開開始時だけ乱数IDの衝突確認1、期限切れ受領記録query最大4。競合時のFirestore transaction再試行分は追加発生する。
- 通報一覧は運営操作時のみ20件。非表示操作時の通報整理も20件まで。
- read/write共通でquotaエラーは429。空の部屋として成功扱いせず、未保存内容を残す。部屋モジュールは生のエラー・キー・個人情報をログに出さない。
- 公開30/分、保存12/分、いいね/通報10/分など既存のrateLimitを使用。これは1プロセスの制限で、分散されたBotの全体readを保証するものではない。公開後は既存インフラの監視で日次枠を確認する。

## マージ後の運用（今回未実施）

マージはオーナーの「マージして」を待つ。本番DB・Rules・索引・Render/Vercel設定を変更していない。

1. PRの変更とテスト証跡を確認する。main更新があれば競合しないことを確認する。
2. `backend/city-room-indexes.json`の索引を既存索引と重複確認して追加する。既存`firestore.indexes.json`をこのファイルだけで置き換えたり、他の索引を削除しない。エミュレーターは本番の複合索引要件を再現しないため、本番索引readyの確認が別途必要。
3. 追加Rulesはserver-only。公開API経由の閲覧に緩和は不要。承認後の通常の配備手順でRulesを公開する。
4. Renderバックエンド→Vercelフロントの順で反映。新しい秘密鍵・有料API・環境変数は不要。
5. 非課金で本人GET、無料3点の保存、明示公開、匿名閲覧、非公開切替を確認する。運営にだけ通報管理が出ることも確認する。
6. 部屋で問題があればフロントのMY CITY入口を前版へ戻し、新ルーターを取り外す。新コレクション・注文・台帳・チェックインは削除しない。非公開化・通報対応が必要ならAPIを先に止めず、運営が対応できる形で切り戻す。

## 再現する環境

バックエンド、guild-tests、quest-tests、economy-testsのそれぞれでlockfile通りに依存をインストールする。Playwright用Chromiumも必要。本検証ではシステムの`/usr/bin/chromium`を使用した。既存テスト用の環境preloadで実行ブラウザーだけを指定し、assertion・商品処理・本番コードを置換していない。

部屋のnative試験は`tools/guild-tests/city-room-native.test.cjs`。Guildのワイルドカードにも含まれるため、全体実行前に**project `demo-city-room`、Auth 9199、Firestore 8787**を起動する必要がある。既存の`firebase.knowledge-lab.json`をローカルのポート定義として使えるが、CLIの`--project demo-city-room`を必ず指定する。別プロジェクトのAuthデフォルトでは、テスト用メールログインが成立しない。既存の本番環境変数で実行しない。demo以外と接続先の不一致は試験コードが拒否する。

- Backend：リポジトリ根で`node --test backend/*.test.js`。
- Emu：リポジトリ根で`node --test tools/emu-tests/*.test.cjs`。
- Guild/City：`node --test --test-concurrency=1 tools/guild-tests/*.test.cjs`。ソフトウェアWebGLの3D試験は数分かかるため、並列による競合を避ける。
- tour/member/admin：それぞれ`node --test tools/<名前>-tests/*.test.cjs`。
- quest-tests：Firestore 8080で、`tools/quest-tests`を作業ディレクトリにして`node --test --test-concurrency=1 *.test.cjs`（既存試験が相対Rulesパスを使用）。
- quest-number/wisdom：Firestore 8080で既存各ディレクトリの試験を実行。
- Knowledge Lab Rules：Firestore 8787。4つのRules試験を実行し、`rules-schedule.test.cjs`はproject `demo-emu-knowledge-lab`の別Auth 9299と`LAB_AUTH_EMULATOR_HOST=127.0.0.1:9299`で分ける。Knowledge Labの製品コードは変更しない。

既存`quest-tests/guild.test.cjs`には「10/1の公開前」を理由にしたskipが4件残る。今回そのソースは変えず、追加の隔離runnerでskipオプションだけを外して同じ15件を実行し、4件を含む全件の元のassertionが通ることを別に確認した。通常コマンドのskip件数を0と偽っていない。

画面写真を更新する場合だけ、`CITY_QA_DIR`にこのPRのevidenceディレクトリを明示し、native部屋試験を単独実行する。通常の試験出力は一時ディレクトリであり、リポジトリ内の画像を自動更新しない。

通常DPR 1の全Guild実行では、既存の3D City 1440pxのタップ/ダブルクリック移動が30秒待機を超える実行があった（最終の通常設定実行は213件中212件合格・1件タイムアウト）。同じ1440px・通常DPR 1の単独実行は合格した。部屋の追加前後で`city-world.js`や3Dテストのassertionは変えていない。
