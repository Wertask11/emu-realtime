## 1. 部屋の見た目と道具

### 推奨：軽い2D等角表示

- 8×6マスの床、左右の壁、窓。SVG＋通常のDOMで少し上から見る部屋を描く。WebGL・物理エンジン・外部CDNは使わない。

## 2. 画面の流れ

1. **マイCityを開く**：従来の訪問・実績一覧を部屋へ差し替える。初期は非公開、無料3点が置かれた部屋。パスポート／星空への小さな導線を残す。既存チェックイン・Quest実績のデータ/APIは維持する。
2. **置く・動かす・回す・しまう**：持ち物を選び、空きマスに置く。不正配置は画面でも示し、保存時はサーバーが再判定。未保存・保存中・保存成功・失敗を明示する。
3. **公式店舗で交換**：「公式ショップへ」で既存の店舗・商品画面を開く。本人が料金・条件・支払いを確認する。部屋側で注文・交換・送金を自動実行しない。
4. **持ち物に入る**：既存注文の `fulfilled` が確認されたものだけを反映。「paid」の間は「引渡し確認中」。店舗から戻る/本人が「持ち物を更新」を押したときに1回取得する。**現行の引渡し処理との調整事項は下記。**
5. **公開・シェア**：保存済み配置だけを公開確認画面で示す。公開が既定でONにならない。「部屋だけが見える／個人情報・パスポート番号・取引履歴は載らない」を明示して公開保存。その後、部屋の画像＋公開URLの共有確認を表示する。
6. **他人の部屋を見る**：`/schoolpark/room.html?id=<publicId>` で閲覧。未ログインでも公開中の部屋だけ見られる。非公開・非表示・存在しない部屋は同じ404。部屋一覧の全件読み込みは追加しない。いいね・通報は正規のログイン後に行う。

### 保存・共有で迷わせない

- 確定は「保存する」。通信断でも画面の未保存配置を消さず、「再送」と「保存済みを開き直す」を出す。同じrequestIdの再送は同じ結果。409なら他方の配置と自分の配置を勝手に上書きせず選べるようにする。
- アカウント切替では進行中通信を中止し、前の人の配置・持ち物・未保存変更・遅れて返った応答を画面へ戻さない。部屋の自動復元に他人のlocalStorageやトークンを使わない。
- 個人の公開名・プロフィール画像・自由入力名は初回の公開データへ含めない。部屋はカタログの道具で構成する。共有画像は部屋の描画部分だけから作り、ヘッダーやパスポート欄のスクリーンショットを使わない。
- Xの投稿画面を開くだけでは画像は自動添付できない。端末がファイル共有に対応すれば本人操作で画像とURLを渡す。非対応時はPNG保存＋URLコピー／X投稿画面の案内まで。自動投稿・X OAuth契約・外部への画像アップロードは追加しない。既に共有先へ渡した画像は回収できないことを公開時に説明する。
- 非公開化したURLは失効し、次に公開するときは新しいpublicIdを発行する案。古いリンクを再び有効にしない。

### 調査で分かった接続上の注意

**A. 「DigitalAssetIdを付ければ登録できる」とは限らない。**
`backend/mitemiru.js` の `cleanProduct()` は `backend/private-assets/catalog.json` に存在し、実ファイルもあるIDだけを認める。現行カタログ5件に `room-…` は0件。

本実装前に交換担当（ChatGPT）へ、上表の10IDに対応するカタログ項目と配布ファイルの登録を調整する。Codexから `mitemiru.js`、`backend/private-assets/catalog.json` を無断で変更しない。必要な項目例は以下（**例であり未登録**）。

```json
"room-desk-oak-v1": {
  "file": "room-desk-oak-v1.png",
  "downloadName": "room-desk-oak-v1.png"
}
```

**B. デジタルのダウンロードはfulfilled化しない。**
現行 `sendDigital()` はpaid/fulfilledの注文を読み、ファイルを返すだけ。部屋は指定どおりfulfilledだけを採用する。現行の運営用 `POST /api/mitemiru/admin/orders/:id/fulfill` は使えるため、初期は運営の既存引渡し確定後に持ち物へ反映する。即時反映まで求める場合は、交換担当によるデジタル引渡し確定の整備が別途必要。部屋側でpaidを所有済み扱いしたり注文をfulfilledへ書き換えたりしない。

**C. 既存の注文一覧を全部の持ち物として流用できない。**
`GET /api/mitemiru/orders` はUID単位の最大200件取得→最新50件を返し、`digitalAssetId`を公開レスポンスへ含めない。部屋APIから、本人のサーバー確定SchoolPark IDに一致する注文を必要フィールドだけで読む。既存APIの上限/レスポンスや履歴を書き換えない。`passportId` がない旧注文をクライアントの申告で他人へ結び付けない。

**D. routerの順序を守る。**
既存City routerは配下の全リクエストへ先に認証を要求する。新room routerをその後ろへ追加すると公開GETまで401になる。新room routerを先に取り付け、公開GETと、認証必須の本人/いいね/通報/運営APIを内部で分離する。

**E. 変更しないファイル・データ。**
`backend/mitemiru.js`、`backend/economy*`、`backend/emuer-v2/*`、`services/polygon-signer/*`、星空/`Emu_room2/*`、`index.html`の星空、既存の認証/会員/報酬・台帳・ゲーム・Knowledge Lab・Camellia。未マージPR #272/#212/#116は取り込まない。チェックイン保存先 `sp_identities/{id}/city_checkins` と既存Cityの `/me`・実績APIを維持する。

## 4. API・保存・Rulesの案

### API

基底 `/api/schoolpark/city/room`。すべて `Cache-Control: private, no-store`。Cookie/トークンの手動注入や別のログインは作らない。

| 方法・パス | 認証・役割 | 内容 |
| --- | --- | --- |
| `GET /me` | 正規Firebase Auth・現在のSchoolPark City入場資格・activeなSchoolPark ID | 既存注文から導いた持ち物、無料3点、配置、revision、公開状態。初回GETではDB文書や報酬を作らない |
| `PUT /me` | 同上・本人のみ | `{requestId,expectedRevision,visibility,layout}` を検証して原子的保存。サーバーが所有者を決定。任意のownerUid/SchoolPark ID/URL/HTMLは受け付けない |
| `GET /:publicId` | 未ログイン可 | 公開かつ運営非表示でない部屋の描画用データといいね数だけ。所有者番号・履歴・全持ち物・注文IDを返さない |
| `POST /:publicId/like` | 正規ログイン＋同一人判定 | 1人1部屋につき1回、再送しても増えない。自分の部屋は除外。公開中の部屋だけ |
| `POST /:publicId/report` | 正規ログイン＋同一人判定 | 同一人は1回。理由は既存と同じ `spam/harass/personal/other` の固定語のみ。任意の通報本文は初回に追加しない |
| `GET /admin/reports` | 既存 `requireOwner` | 明示的に開いたときだけ、最大20件ずつカーソルで確認 |
| `POST /admin/moderation` | 既存 `requireOwner` | 運営の非表示・再表示。本人の公開/非公開を勝手に変更しない。運営非表示を本人が保存で解除できないようにする |

取得できなければ503/429で止める。「持ち物0個」と見なして保存済み家具を消す処理はしない。保存時に不正なら400/403、所有/公開範囲のない閲覧は404、競合409、同じrequestIdで別内容も409。

### 持ち物の正本とサーバー検証

新しい部屋用品の注文について `passportId=本人`、公式店舗/公式ショップ、`status=fulfilled`、`digitalAssetId`がroomカタログにある `room-…` の注文だけを読む。`paid`、取り消し、返却済み、他人/他店舗の注文、未知IDは所有数へ足さない。現行注文は1件1個なので、注文原本を1回ずつ数える。将来のquantityをクライアントの申告で推定しない。

保存トランザクションでcurrentな注文の所有・引渡し状態と配置を照合する。回転後の床占有/壁枠/個数/総数/座標範囲、設定枠ごとの種類、未知フィールドを検証し、publicId以外の識別子を公開用JSONへ漏らさない。家具を返却した場合に再配置できないことも試験する。

本人GET/公開GETでも、置いている有料道具の根拠注文が現在有効かを必要な原本だけで確認する。返却/取り消し等で失効した道具は非表示＋本人へ理由を示し、元の配置データを勝手に削除しない。公開GETを「常に2read」とは約束しない（下記の負荷）。

### 新規保存領域（1つのトップレベルの配下に分離）

- `city_rooms/{SchoolPark ID}`：本人の部屋。`schemaVersion, ownerUid, schoolParkId, revision, visibility, layout, publicId, createdAt, updatedAt`。`ownerUid`は最初の作成者の監査情報、所有判定の正本は毎回サーバーで解決した同一SchoolPark ID。
- `city_rooms/_public/ids/{publicId}`：公開ID→部屋の私的な対応表。暗号学的乱数128bit（22文字のbase64url等）。公開・非公開の状態と失効を保持。GETはこの対応表と部屋を読む。
- `city_rooms/{SchoolPark ID}/likes/{本人識別ハッシュ}`：同一人の重複を防ぐ。誰が押したかを公開しない。
- `city_rooms/{SchoolPark ID}/city_room_reports/{本人識別ハッシュ}`：通報。運営以外の人へ一覧を返さない。
- `city_rooms/{SchoolPark ID}/requests/{requestId}`：保存の冪等応答。同じキー/本文を確認。サイズ上限と7日保持の案。期限後もexpectedRevisionが古い再送を新規保存として通さない。
- 部屋本体と持ち物の履歴は、マイCityのために既存注文を削除・移行しない。room本体の保存期間は初回「本人が非公開にしても保持」が案。削除機能/アカウント削除連携は、既存方針を確認して別途設計する。未承認の定期削除・画像外部保存を追加しない。

通報は、たまり場と同じ「違う3人の有効な通報で、運営が確認するまで非表示」を案とする。運営の確認・再表示の扱い、同一人重複、自分への通報拒否も揃える。匿名の閲覧と、ログイン必須のいいね/通報を混同しない。

```rules
// SchoolPark City の部屋。公開・本人確認はサーバーAPIだけで行う。
match /city_rooms/{document=**} {
  allow read, write: if false;
}
```

この1ブロックで_publicの対応表・likes・通報・冪等記録の配下も閉じる。現mainの汎用受け皿は `legacyOpenCollection()` がfalseなので、新コレクションが別matchから公開許可される状態ではない。Claudeの `sp_star_layouts` 等の追加と競合したら、どちらも残して拒否テストを行う。本番Rulesはオーナーの公開承認前に更新しない。

### 読み取り上限・小さい負荷から始める

- 部屋への入場時に1回。ドラッグ中0通信、保存は本人操作、交換から戻ったとき/更新操作にだけ持ち物を取得する。常時ポーリング・onSnapshot・部屋一覧走査は追加しない。
- 持ち物は、本人＋既知のroom- ID＋fulfilledを絞る注文queryを上限付きで使用し、必要なフィールドだけ読む。初期案は64件＋上限検出1件。超えたら空や一部を完全な持ち物と偽らず、更新不可を説明して追加設計へ。最新50件だけに切り捨てない。新索引の要否は分離環境で確認する。
- 公開部屋は対応表＋部屋の2文書に、配置された有料道具の根拠注文の再確認を加える。最大24配置なら概算2〜26文書。無料だけなら2文書、認証/いいね等は別。26readの部屋が1,000回見られれば約26,000readになるため、閲覧rate limit・観測・負荷試験なしで無制限公開しない。
- 配置/無料カタログの絵と対応表は同梱。静的配信はAPI/個人データと分けてキャッシュする。公開状態の判定を古いCDNキャッシュで飛ばさない。
- rate limitには現行のプロセス内バケットの限界がある。複数拠点の厳密な日次制限が完成したとは扱わない。Firestore 429では受付/保存を安全に止め、未保存配置を保持する。読み取り不能時の削除/空保存はしない。
