# Founder向け運営手順

この文書のURLは公開後の予定URLです。最終報告の公開判定がREADYになるまで、利用可能と案内しないでください。

## 最初の公開

1. 手動で最新 `firestore.rules` をFirebaseコンソールに公開する。`firestore.indexes.json` の `knowledge_lab_notes` 複合インデックス（visibility ASC / authorSchoolParkId ASC / __name__ ASC）もコンソールまたは既存の正規デプロイ手段で作成する。特に `knowledge_lab_.*` の包括許可除外と、`posts` のサーバー専用メタデータ保護が必要。
2. PRの自動テスト・Previewの静的画面・認証・保存・既存回帰を確認する。Previewは本番APIを共有するため、本番利用者データで保存テストしない。
3. 検証済みPRをmainへ反映し、Render/Vercel両方の完了を確認する。Renderの `KNOWLEDGE_LAB_ENABLED=true` を設定するまで新APIは保存を受け付けない。
4. 既存OwnerアカウントでEmuへログインし、「知識を探す → Knowledge Lab → 運営管理」を開く。サーバーの匿名読み取り拒否確認に失敗した場合は利用を停止し、Rulesを再確認する。
5. 「初期分類を登録」を1回押す。既にある分類は上書きしない。
6. 「公開投稿の検索索引を作成・再確認」を押す。正本は25件ずつ読み、公開内容だけから索引を作る。活動状況が `ready` になるまで待ち、検索が正しく返るか確認する。
7. 本番で本人の既存記録を破壊しない範囲の確認を行う。機能利用の権限・範囲を確認してから募集URLを案内する。

## 日々の運営

- **書き手**：登録数、直近7日の新規数、一覧を確認する。経験・資格は自己申告。資格確認がない人に認証済み表示を付けない。
- **投稿**：公開経験知数・分野別数を確認する。6か月以上更新がない知識は、日付・制度・使用条件を確認して投稿者に更新を依頼する。更新依頼はこのアプリから自動送信されない。
- **分類**：内部IDを一度決めて保存する。表示名の変更はIDを維持する。追加・非表示・同軸の統合が可能。統合元IDは削除しない。既存投稿への分類付与は投稿ID・現在の版番号・理由を入力し、本文を変更せず保存する。
- **募集**：未回答の問いと回答数を確認する。回答・採用は既存画面を使用する。EMUERの既存審査・上限・トレジャリー処理を維持し、Lab独自の報酬を約束しない。
- **研究**：元知識の参照と、未検証の仮説／実践結果の区別を確認する。研究は人による作成。AI生成費用は発生しない。
- **通報**：対象・理由を確認→必要なら公開を停止→対応メモを記録→確認中／対応済み／対応不要を選ぶ。公開投稿の停止は非公開領域への保管で、本文を破壊しない。復元できるのは運営が停止した元公開投稿だけ。利用者の自分用記録を勝手に公開しない。
- **検索**：通常投稿後の索引更新は親画面から、予約投稿は既存サーバーから実行する。通信失敗時は索引再確認で修復する。キャッシュは通常60秒ごとに更新分を取得し、1時間ごとに全体を再確認する。索引は派生データなので、壊れても正本の `posts` は消さない。

## 費用と制限

外部検索サービス・有料AI・新課金は契約していない。既存FirestoreとRender/Vercelの費用は発生しうる。

- 初回索引：公開投稿1件につき少なくとも正本1読み取り・索引1書き込み。
- キャッシュの取得：索引を128件ずつ読み、最大20,000件・JSON換算64MiB。完全な検索対象を用意できない場合、部分結果を完全検索と表示せずエラーにする。
- 検索結果：通常20件を正本から再確認。削除された候補が多い場合は追加読み取りが必要。
- サーバーキャッシュは通常60秒ごとに更新分を確認し、1時間ごと・索引再作成後・プロセス再起動時に全体取得が必要。複数インスタンスでは各インスタンスが独立して取得する。
- 管理集計はFirestoreのcount集計を使う。分野別集計には分野数に応じた問い合わせが発生する。
- 通常APIは90回/分、保存APIは20回/分、運営APIは30回/分。投稿・募集・回答の月間利用枠は既存制度を共有。
- 書き手あたり研究ノート1,000件、保存知識1,000件。本文5,000字、検索文書64KiB（超過は切り捨てない）、元知識2〜6件、研究分野2〜3つ、分類400件。

Firebase使用量画面・Renderメモリ／エラーを確認する。上限を超える規模では検索基盤を別途検討する。無断で有料サービスを有効化しない。

## 障害・ロールバック

1. 新機能の障害はRenderの `KNOWLEDGE_LAB_ENABLED=false` で停止する。既存ログイン・投稿・Room1等は別ルートのまま。
2. Vercel/Renderを直前の安定コミットへ戻す。Firestore Rulesは新規領域の拒否を維持する。古い包括許可へ戻すと非公開Labデータが漏れる。
3. コレクションを削除する必要はない。既存投稿の正本と過去データは維持する。
4. Labメタデータのある投稿を古いアプリで直接編集しようとするとRulesが拒否する。機能を再公開してLab編集画面を使用するか、安全な個別復旧を行う。

## 開発者向け・本番を使わない確認

```sh
npm ci --prefix backend
npm ci --prefix tools/quest-tests
FIREBASE_EMULATORS_PATH=/workspace/.cache/firebase/emulators XDG_CONFIG_HOME=/workspace/.cache/firebase/config CI=1 node tools/quest-tests/node_modules/firebase-tools/lib/bin/firebase.js emulators:start --only auth,firestore --project demo-emu-knowledge-lab --config firebase.knowledge-lab.json
```

別ターミナルで `node --test tools/knowledge-lab-tests/lab.test.cjs`、`node --test tools/knowledge-lab-tests/rules.test.cjs`。ブラウザ検証はテスト終了後に `node tools/knowledge-lab-tests/fixture.cjs` → `python tools/knowledge-lab-tests/browser.py`。fixtureは `demo-emu-knowledge-lab` のローカルAuth/Firestore以外を拒否し、起動時にその検証データだけを初期化する。同じ検証DBを使用するため、fixtureとAPIテストを同時に動かさない。

本番のアカウントを作成すること、本番トークンを偽装すること、本番利用者の記録をテスト用に変更することは禁止。テストアカウントとデータの作成は、許可されたローカルエミュレーター内に限定する。
