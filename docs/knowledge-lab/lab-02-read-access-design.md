# LAB-02 見学（guest）の「新着20件」と公開投稿の配信経路：対応表と設計案（2026-11-07）

**この文書は設計の案です。閲覧の権利・Firestore Rules・既存の一覧は変えていません。**
「新着20件」が、権利として守る境界なのか、画面で見せる範囲なのかは、創業者が決めることです。決まるまで、どの経路も今のまま動きます。

## 1. いまの約束（コード上の正本）

| 場所 | 内容 |
|---|---|
| `backend/membership-policy.js` の `catalog()` | `readerScope`：guest は `"latest-20"`、light・plus・pro は `"all-public"` |
| 料金ページ（membership-plans.html） | 見学は「読む・見る」。新着の一部 |

## 2. 公開投稿（`posts`）の本文が届く経路

| # | 経路 | 誰が | 20件の制限 | 根拠 |
|---|---|---|---|---|
| 1 | 知識を読む（`index.html` の一覧の読み込み） | ブラウザ → Firestore（SDK） | **画面で**20件までに切る。読み込み自体は Rules で `read: true` | `index.html` 28654・29033〜29078 |
| 2 | 投稿1件のシェアページ `/p/<ID>` | Vercel 関数 → Firestore REST（匿名） | **なし**。ログインしていない人に本文を返す（SNS のカードのため） | `frontend/api/emu-post.js` |
| 3 | Knowledge Lab の検索 `/api/knowledge-lab/search` | Render → Admin SDK | **あり**。guest は新着20件の中だけを探す | `service.js` search（guest の scope） |
| 4 | Knowledge Lab の投稿詳細 `/api/knowledge-lab/posts/:id` | Render → Admin SDK | **あり**。新着20件より古い投稿は 403 `READER_PLAN_REQUIRED` | `service.js` rawPost |
| 5 | Firestore を直接読む（REST・SDK） | 誰でも | **なし**。`match /posts/{postId} { allow read: if true; }` | `firestore.rules` 680〜681 |
| 6 | Good・Change・ギルド・クエスト・パスポートなどの画面 | ブラウザ → Firestore | なし（投稿1件ずつ読む） | `index.html` 6946・20937 ほか、`change-reflection-ui.js` |

**Codex の再現（LAB-02）と同じ結論**：経路4は古い投稿を 403 で断ります。一方、同じ投稿は経路5で、ログインせずに読めます。非公開のデータ（下書き・研究ノート）が漏れているわけではありません。公開済みの本文の「どこまで見せるか」が、経路ごとに違っています。

## 3. 選択肢

### 案1：「新着20件」は画面で見せる範囲と決める（権利ではない）
- **変えるもの**：料金ページ・Lab の文言で「見学では新着の一部を一覧で表示」と説明する。経路4の 403 は、案内（「light で全部を一覧で探せます」）に置き換えるか、そのまま残す。
- **影響**：既存の一覧・シェア・SEO・Good などは変わらない。作業は小さい。
- **リスク**：無料で古い投稿を直接読めることを、仕様として認めることになる。

### 案2：「新着20件」を権利の境界にする（段階的に移す）
1. 公開本文を読む経路を、すべて「共通の認可 API」（Render）に寄せる。経路1・6をここから読むように変える。
2. 経路2（シェアページ）は、カードに必要なタイトル・要約・画像だけを返し、本文は認可 API を通す。
3. すべての画面が認可 API に移ったことを、本番で確かめる。
4. 最後に、Rules の `posts` の `read` を、本人の投稿・反応の更新に必要な範囲に絞る。**ここで初めて Rules を変える。**
- **影響**：大きい。読み込みが Render を通るので、速さ・費用（Render の負荷、Firestore の読み取り）・落ちたときの影響が増える。検索エンジン（SEO）や SNS のカードの見え方も変わる。
- **期間の目安**：段階1〜3で、画面ごとの改修とテストが必要（数日〜1週間）。

### 案3：中間（公開インデックスを分ける）
- 一覧・検索・カードに使う「公開インデックス」（タイトル・要約・作成日だけ）を作る。本文は、ログインと段に応じて認可 API から返す。
- 案2より軽いですが、データの持ち方が2つになります。

## 4. 今回やらないこと（指示書どおり）
- `posts` の read Rules を閉じること
- 無料・見学の閲覧の権利を増やしたり減らしたりすること
- 今の一覧（知識を読む）を壊すこと
- 契約している人の権利を変えること

## 5. 決めてほしいこと
1. 「新着20件」は、権利の境界か、画面で見せる範囲か。
2. 権利の境界にするなら、シェアページ（`/p/<ID>`）で本文をどこまで見せるか。
3. 移す順番と時期。案2は、Render の負荷と費用の見通しを先に出します。

## 6. 移すときのテスト（案2を選んだとき）
- 経路ごとに、guest・light・plus・pro・公式パス・Owner で「読める・読めない」が同じになること（表で期待値を固定する）。
- 画面の一覧・Good・Change・クエスト・パスポートが、認可 API に移ったあとも同じに動くこと。
- Rules を絞る前に、本番で直接読む経路が残っていないこと（Firestore の利用ログで確かめる）。
