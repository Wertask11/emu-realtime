# SchoolPark・Emu 調査報告：通信が遅い・読み込みが遅い（2026-10-16）

調べた範囲：main `f52dc21`（#216 まで）、本番の Render（サーバー）・Vercel（画面）・Firestore。
測り方：Render の記録（起動・メモリ・CPU・ログ）、本番 URL の実測、ブラウザ（スマホ幅・CPU を4分の1に落とした状態）での読み込み、公開データでの Firestore 読み込みの再現。
**ログインした状態は試していない**（ログインを偽装しない約束のため）。ログイン後の流れは、コードと公開データから再現した。

## 1. サーバーが無料プランで、たびたび眠る（最優先）

**事実**
- 本番サーバー `emu-realtime`（Render）は **Free プラン**、場所は**アメリカ・オレゴン**、台数1。
- 無料プランは、しばらくアクセスがないと止まり、次のアクセスで起動し直す。
- 起動し直した記録（「Emu Server running」）は、10/14〜10/16 の3日で約50回。更新による再起動を除いても、**日本時間の日中に20分〜1時間おき**に起きている。
  - 10/16（日本時間）：9:03、9:20、10:04、11:05、11:39、13:02、17:19
- 起動の合図から受け付け開始まで、毎回約7秒かかる（例：17:19:14 → 17:19:22）。これに、Render がサーバーを用意する時間が上乗せされる。
  - 手元では、部品の読み込みに約0.5秒しかかからない。無料プランは CPU が小さいので、それだけで長くなっていると考えられる。
- 温まっているときの応答は 0.6〜1.0秒（この環境から）。日本からだと、オレゴンとの往復の分が毎回加わる。

**影響**
- ログインの流れ（`_emuEnsureServerAccount` → `entry-status` → 着地）が全部このサーバーを通る。
- サーバーが眠っていると、コードの待ちが段階的に重なる。
  - 8秒待つ → 30秒で取り直す（`index.html` 6685行付近）
  - 入場の確認は20秒（23200行付近）
  - 着地は12秒、さらに最大60秒（9457〜9465行）
- 「ログイン後に画面がなかなか出ない」「真っ白」（10/13 に直した件）の大もとは、ここ。

**直し方の案**
1. **Render を有料の Starter（月 $7 前後）にする** — 眠らなくなり、CPU も増える。いちばん効く。設定を1か所変えるだけ。料金はオーナーが決める。
2. あわせて、**日本に近い場所（シンガポール）**で動かす — 往復の遅れが減る。Render は既存サービスの場所を変えられないので、新しく作って移す作業になる。
3. お金をかけない応急策：外から定期的にアクセスして眠らせない。無料プランの使い方としては推奨されないので、勧めない。

## 2. 最初に読む画面ファイル（index.html）が 1.35MB

**事実**
- `frontend/public/index.html` は 1,352,424 バイト。
  - 中に直接書かれたプログラム：20か所・1,028,956 バイト
  - 見た目の設定（CSS）：197,120 バイト
- 送るときは圧縮されて 372KB になるが、ブラウザは元の大きさを全部読み解く。
- 実測（ログイン前の最初の画面、390px）

  | 条件 | 表示まで | 固まった時間の合計 | いちばん長い固まり |
  |---|---|---|---|
  | 速い CPU | 3.4秒 | 1.7秒 | 0.5秒 |
  | スマホ並み（CPU を4分の1） | **5.6秒** | **3.2秒** | **1.3秒** |

**直し方の案**
- プログラムを別のファイルに分けて、ブラウザに取っておけるようにする（2回目からは読み直さない）。
- 最初の画面に要らない機能（ゲーム、ウォレット、管理系など）は、使うときに読む。
- 一度に全部ではなく、効果の大きい部分から分ける。

## 3. 全ファイルが「毎回、更新を確かめる」設定

**事実**
- `vercel.json` の `headers` が、すべてのファイル（`/(.*)`）に `Cache-Control: public, max-age=0, must-revalidate` を付けている。
- 画像・フォント・JS も含めて、開くたびにファイルごとに「変わっていないか」をサーバーに確かめる。
  - 最初の画面だけで、同じ場所への読み込みが26件ある。

**直し方の案**
- HTML だけは今のまま「毎回確かめる」にする。
- 画像・フォント・JS・CSS は長く取っておけるようにする（JS・CSS はファイル名に版を付ける）。

---

## 4. ロゴ画像が 2.1MB

**事実**
- `logo.jpg` は 2,097,608 バイト・1024×1024 で、最初の画面（`#logoImg`）に小さく表示している。
- ほかに、OGP（SNS でリンクを共有したときの画像）にも使われている。

**直し方の案**
- 表示用に、小さな WebP（数十KB）を別に作る。OGP 用は今のまま、または 1200×630 のものに分ける。

---

## 5. ウォレット用ライブラリを全員に先に読ませている

**事実**
- `ethers@5.7.2`（760KB、圧縮で 190KB）と `socket.io`（50KB）を、`<script src>`（defer なし）で読んでいる（6151・6163行）。
- このため、残り約2万3千行の画面の読み込みが、2つのダウンロードと実行が終わるまで止まる。
- ethers が必要なのはウォレットを使うときだけ。ゲスト・LINE ログインの人には要らない。
- socket.io はページを開いた直後からサーバーにつなぐ（ログイン前のゲストも）。

**直し方の案**
- ethers はウォレットの操作をしたときに初めて読む。
- socket.io は defer にして、必要な画面で接続する。

## 6. 同じ設定を1ページで6回取りに行く

**事実**
- `/api/emuer/v2/config` を、次の6つのファイルが別々に取りに行く。
  - `emuer-v2-cutover-ui.js`
  - `emuer-v2-public-copy.js`
  - `discussion-reward-ui.js`
  - `guild-quest-rewards-ui.js`
  - `change-reflection-ui.js`
  - `wallet-success-ui.js`
- ブラウザの実測でも、1回の読み込みで6回届いていた。
- サーバーが眠っていると、6本とも起動を待つ。

**直し方の案**
- 1回だけ取りに行き、結果を6か所で使い回す（共通の読み口を1つ作る）。

## 7. SchoolPark を開くと Firestore へ52回読みに行く

**事実**
- `spDaoReloadAll` が、9種類の読み込みを並べて走らせる。
- そのうちクエストは、22本それぞれについて「受けた人（commits）」と「報告（logs）」を別々に読む。
- 本番の公開データで同じ読み方を再現すると、**52回の通信**になった。
  - 時間は 1.8秒、通信1回あたり中央値 74ms（この環境から）
  - 日本の端末からは、往復の遅れ×回数で長くなる
- 普通の通信は、一度に3本まで（`_spRestState` の `max: 3`）。
- 5分ごとの読み直しで、これを繰り返す。クエストが増えるほど回数が増える。

**直し方の案**
- サーバーで「クエストごとの受けた人数・報告数」をまとめて、1回で返す。
- それまでの応急策として、一度に流す本数を増やす（3 → 8 程度）。
- 一覧画面では件数だけを読み、詳細は開いたときに読む。

## 8. SDK を4秒待ってから普通の通信に切り替える作りが7か所

**事実**
- Firestore の SDK（常時接続）が返事をしないと、4秒待ってから普通の通信で読み直す。
  - 対象：`_spReadAll`、知識を探す、ほか計7か所
- 一度待ちきれなかったら、60秒は SDK を使わない仕組みはある。それでも、最初の1回はどの画面でも4秒待つ。
- コードのコメントにもあるとおり、パソコンでは常時接続が止まりやすい。

**直し方の案**
- 一覧を読むときは、最初から普通の通信を使う。常時接続は「変わったら知らせる」だけに使う。

## 9. LINE ログインの失敗（今日2回）

**事実**
- Render のログに `LINE token error: invalid_grant / invalid authorization code` が、10/16 の 13:04 と 19:09（日本時間）に出ている。
  - 1回目は、サーバーが眠りから起きた2分後。
- LINE の認可コードは1回しか使えない。コードを2回送るか、期限が切れると、この失敗になる。
- 画面側（28462行付近）は、送り直しも待ち時間の上限もない1回きりの送信。失敗すると「もう一度お試しください」になる。

**原因は未確定。**
- 候補1：LINE アプリから戻るときに、ページが2回開いてコードが二重に使われた。
- 候補2：サーバーが眠っていて待つ間に、利用者がもう一度ログインを押した。
- 本人の操作記録がないので、どちらかは分からない。

**直し方の案**
- 同じコードを二重に送らないように、画面側で印を付ける。
- 失敗したら、LINE ログインをもう一度最初から始める案内に直す。
- 1（サーバーの眠り）を直すと、候補2は消える。

## 速さ以外で見つけたこと

- **Render に同じアプリのサービスが5つある**（`emu-realtime`、`emu-realtime-1`〜`-4`）。
  - どれも main の更新で毎回組み立て直している。画面から使われているのは `emu-realtime` だけ。
  - 使っていない4つを止めれば、組み立てにかかる時間の無駄が減る。止めるかはオーナーが決める。
- 組み立てのたびに「`package-lock.json` と yarn が混ざっている」という警告が出ている（実害は今のところない）。

## 確かめて、問題がなかったこと

- 今日の #215・#216 がサーバーに反映されていないのは正常。画面側だけの変更で、Render はサーバーの部品（`backend`）が変わったときだけ組み立て直す設定。
- 屋台ゲーム6つの埋め込み画面は、開いたときに作られる。最初の読み込みには影響しない。
- 3D の街（City）のライブラリ（544KB）は、City を開いたときにだけ読む。
- サーバーのメモリは 120〜205MB（上限 512MB）、CPU の使用率は低い。メモリ不足の再起動は見当たらない。

## 確かめられなかったこと

- ログインした状態での実際の待ち時間（ログインを偽装しないため）。
- Firestore のデータがどの地域にあるか（日本からの往復時間）。
- 実際の利用者の端末での表示速度（Vercel の速度計測は使っていない）。

## 直す順番の提案

1. **Render を有料プランにする**（オーナーの判断。直後から効く）
2. **すぐ直せて効くもの**（1日でできる、画面側だけ）
   - ロゴを小さくする（#4）
   - ethers を使うときに読む（#5）
   - 設定の6回取りを1回にする（#6）
   - ファイルを取っておける設定にする（#3）
   - Firestore を一度に流す本数を増やす（#7 の応急策）
3. **少し時間がかかるもの**
   - index.html を分ける（#2）
   - クエストの件数をサーバーでまとめる（#7）
   - SDK の4秒待ちをやめる（#8）
4. LINE ログインの二重送信を防ぐ（#9）
