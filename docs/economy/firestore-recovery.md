最新mainの画面側の読取抑制（#301〜#303）とLab側の安全確認間隔変更（#304）を取り込む。今回、Knowledge Lab本体・UI・データモデル・Rulesは変更しない。新しい課金・EMUER消費・AI生成は行わない。

## 判定の根拠

本番の本人画面では、承認済み1件が5 EMUER・完了/提供完了、公式案内とGuildを横断する根拠付き結果を表示した。最終原本照合はFirestore RESOURCE_EXHAUSTEDで未完了だった。今回も最小の検索型読取がcode 8/HTTP429となり、workerはnot_ready・受付は安全側で停止。単一文書のSDK読取成功も一度確認したが、後続の読取が失敗するため全面復旧とは判定しない。

読み書き確認は、サーバー専用の新しい運用probe文書を1件だけ作成し、読取を試し、最後に削除した。作成・削除は成功（計2書込）、読取はcode 8。probeは削除済み。ユーザー情報・台帳・注文・資料同意・履歴は書き換えない。失敗した読取の高頻度再試行は避ける。

Service Usage APIで確認済みのFirestore読取上限は50,000/日。このAPIの上限設定は「実使用量/残量」を返さないため、正確な残りクォータや回復時刻は未確認とする。無料枠をリセットしたり、Billing・カード・有料契約を変更したりしない。

Phase 2のPASSには、この同じ1件の台帳・注文・ジョブ・結果・履歴の照合、重複請求/返却漏れなし、6領域19資料の現行確認、worker healthyと受付の正常復帰が必要。未照合を成功とみなさず、再度の本番課金で代用しない。

## 読取が増える経路

- 従来のworker：30秒ごとに未完了5状態をそれぞれ検索。空でも5検索の最低課金読取が発生。readinessの3文書と合わせて最低8読取/周期、常時起動なら約23,040読取/日。共有50,000枠の約46%に相当し、通常利用は別に加算される。削除対象の確認3検索/時や実際のジョブ/返却/トランザクションはこの見積もり外。
- 履歴：最大100件を問い合わせ、表示対象の各依頼をview経由でさらに1文書ずつ再読込していた。50件表示なら最大50読取が重複。注文/返却状態の最新確認は別に必要。
- 画面側：SchoolParkの全体ロードは複数コレクションと子の参加/報告/引用を読む。以前のランキング・フィード・画面復帰時・定期更新と併せて利用者/タブ数に比例して増える。#301〜#303がキャッシュ/更新間隔/非表示ランキングを修正済み。
- Lab安全確認の間隔は別担当が#304で修正済み。今回は変更しない。

これらはコードから確認できる増加要因。プロジェクト全体の時系列使用量や内訳を取得できていないため、単独の原因・割合と断定しない。

## 今回の修正

1. workerは未完了5状態に対するindexed IN queryをlimit(1)で行い、空なら処理を終える。通常の空周期は1検索＋3 readiness文書で約11,520読取/日、最低分を約50%削減する。
2. 未完了がある場合は従来の状態別検索と処理順を維持する。支払復旧→queued→実行を同じ周期で処理し、多数のqueued/過去のcompletedによって返却・保存済み結果の引渡しを取りこぼさない。非空周期は存在確認1読取が追加される。
3. 履歴は本人spidで取得したsnapshotを再利用する。整形関数でもspidを確認し、注文状態は毎回最新を読む。個別詳細の所有権読取、資料権限・投稿者AI同意・原文/ハッシュの再確認は維持し、キャッシュで迂回しない。
4. Firestore code 8/RESOURCE_EXHAUSTED/明確なquota exceededの周期エラーだけ、60/120/240/300秒へbackoff。待機中の30秒timerはDBを呼ばない。受付は不健全状態で停止したまま。通常の30秒復旧と、新規queued時の即時wake、期限/リース/90秒健全性有効時間、決済/返却の整合性は維持。
5. 公開statusは従来どおりDBを読まず、retryAfterMsだけを追加する。クォータ復旧後の最初の正常な周期でbackoffを解除する。結果の再生成・再課金は行わない。
