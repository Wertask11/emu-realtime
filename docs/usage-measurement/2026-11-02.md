## PostHog destination and privacy

Founder explicitly approved reuse of Camellia's current PostHog project in this task. Reuse only its public project capture token and US ingestion host; do not expose it in logs/reports. No personal API/admin token is required for capture, but dashboard verification needs an authenticated project viewer. We use the same minimal allowlist and durable-delivery principles, without adding the PostHog SDK/autocapture/replay/person profiles or SDK URL/device metadata.

Collection starts only after the visitor permits it in that browser; `privacy.html#usage-measurement` lets them stop or permit again. DNT/GPC suppress sending. The consent prompt is shown only in the parent app or standalone knowledge/Lab. A same-origin iframe shares its parent's sender and session. Login IDs are never used. Anonymous random visitor UUID is localStorage; session UUID and pending queue are sessionStorage. Maximum queue 100, age 24h; withdrawal clears pending and anonymous identity. Browser closure normally removes sessionStorage; restoration may preserve it until expiry. Retry keeps UUID/`$insert_id`; batches remove only acknowledged packets. HTTP/network failure is pending, never shown as success. Privacy explains the receiving service necessarily sees the transport IP; payload overrides stored IP and disables geolocation enrichment.

Common properties: `service=emu_for_schoolpark`, `environment=production|preview|local`, `traffic_type=user|internal`, anonymous `distinct_id`, `$session_id`, `$insert_id`, timestamp, `$process_person_profile=false`, `$geoip_disable=true`, zero IP override. No URLs/referrer/query/hash, account IDs, user-auth data, content, amounts or reward values. `credentials:omit` and `referrerPolicy:no-referrer`.

### Events and funnels

| Event | Actual trigger / safe properties |
|---|---|
| `session_start` | First permitted activity per tab session; shared iframe sender |
| `knowledge_list_view` | List response rendered and visible; `surface=feed` |
| `knowledge_detail_view` | Actual text expansion, source sheet after successful read, or Lab detail; `surface=feed|source|lab` |
| `post_create_start` | Composer actually opened; `surface=feed|lab|legacy` |
| `post_publish` | Successful batch commit, or Lab PUT public publication/transition from non-public; `surface=feed|lab` |
| `knowledge_action` | Persisted helpful/improvement success; actual source-linked discussion form opened; `action=helpful|improvement|discussion` |
| `quest_list_view` | Loaded visible quest list, including confirmed empty list |
| `quest_detail_view` | Visible detail with a loaded matching quest |
| `quest_join` | Server read-back confirms a new participation record |
| `quest_complete` | Existing server reads observe increased approved rounds for this visitor; initial historical snapshot does not count |
| `knowledge_lab_view` | Available visible Lab section; `section=library|research|mine|requests|writer`; admin excluded |
| `knowledge_lab_search` | Successful search rendered; `mode=lexical|semantic`, bounded integer `result_count`, boolean `more` |
| `knowledge_lab_research` | Actual comparison, accepted AI result or successful note save; `stage=compare|ai_success|save`, `method=manual|ai` |
| `knowledge_lab_writer_profile` | Own writer form viewed or successful profile PUT; `stage=view|save` |
| `knowledge_lab_save` | Successful bookmark/note/private draft persistence; `kind=knowledge|research|draft` |

No `quest_start`: there is no independent persisted start stage. Quest completion records **observed in an active permitted browser** are measurable; this is not a complete server ledger of approvals while users are offline. Historical completions are never fabricated as new. Shared public `/p/:id` pages keep their existing script-disabled CSP and are not instrumented; feed/source/Lab detail routes are covered. Discussion action measures reaching the real form, not saving an unsubmitted proposal. Local dedupe keys may use resource IDs in memory; keys are never sent.

Funnels: session → knowledge list → detail → create → publish; detail → action by enum; quest list → detail → join → observed completion; Lab view → search → compare/AI → note save; Lab writer view → writer save. Build each with filters **service=emu_for_schoolpark AND environment=production AND traffic_type=user**; otherwise Camellia/session events and internal tests would mix.
