## 1. Emu とは何か

| 項目 | 内容 |
|---|---|
| 運営 | 合同会社型DAO SchoolPark（オーナー1人） |
| 正式タグライン | **「あなたの熱に、ついてこられる場所。」** |

### 主な機能

議論（その日限り・JST 0:05リセット）／遊び（ECHO FIELD・林檎の方程式）／
価値プロフィール／星空（行動を5種類の星で可視化）／EMUER（アプリ内ポイント）

## 2. 商品の全体像 ★これが今回の中心

**商品は3つ。その手前に無料見学モードを置き、全体で4段階。**

| 段階 | 価格 | 役割 | 商品階段での位置 |
|---|---|---|---|
| 無料見学モード | 0円 | Emu が何かを理解する | 入口（商品ではない） |
| **Emu light** | 月額 500円 | 知識交換を1回体験する | **フロントエンド商品** |
| **Emu plus** | 月額 3,000円 | 学びを継続・蓄積する | **ミドルエンド商品** |
| **Emu pro** | 月額 10,000円 | 契約済みの対話機会を通じて前進する | **バックエンド商品** |

**言い方**：体験する → 継続・蓄積する → 対話で前進する

### 重要：3プランがそのまま商品階段である

フロント／ミドル／バックエンドは、**3プランとは別に用意する単発商品ではない。**
light がフロント商品そのもの、plus がミドル商品そのもの。すべて月額サブスク。

### 各段の強み

| 段 | 強み | 効くセグメント |
|---|---|---|
| 見学 | **身銭を切る前に、中の空気を自分の目で見られる**（決済情報も不要） | 来たばかりの人 |
| light | **出した経験に、必ず応えが返る**（他人の反応は運だが、運営の応答は約束できる） | 煙たがられる人・発言できない人・話しすぎて引かれる人 |
| plus | **やったことが、消えずに積み上がる**（保存・整理・月次の学びの軌跡） | 独学に限界を感じる社会人 |
| pro | **一人では止まる思考を、止めない相手がいる**（相手が決まっている＋保証） | 語れる相手がいない・SNSでは深まらない・ライバルがいない |

### pro は機能表の一列ではない

pro は plus の上位グレードではなく**別カテゴリ**。販売画面では機能表を plus で終わらせ、
pro はその下に別枠で置く。機能表に並べると「差額7,000円で4行だけ？」に見えるが、
実際は対話4回で1回あたり1,750円。**対話そのものが商品**であり、
対話以外のオマケを足すほど「proは対話だ」というメッセージが薄まる。

## 3. 上限（9月1日から）

| 機能 | 見学 | light | plus / pro |
|---|:--:|:--:|:--:|
| 知識を届ける（投稿） | 0 | **月2件** | **月30件** |
| 知識を募集する | 0 | **月1件** | **月10件** |
| 募集へ回答する | 0 | **月5件** | **月30件** |
| 一日シェアを記録する | 0 | **月7日** | **毎日** |
| 議論を作成する | 0 | **なし** | **月10件** |
| マイライブラリー | 0 | **30件** | **1,000件** |
| 議論への発言 | × | ◯ | ◯ |
| 読む・見る | ◯ | ◯ | ◯ |
| 4言語（ja/en/zh/ko） | ◯ | ◯ | ◯ |

### 設計の理由

- **「拡張」「無制限」という言葉を使わない。** 顧客にも開発者にも意味が確定せず、規約に書けない。
  「無制限」より十分に大きい上限のほうが、荒らし・自動投稿・想定外コストを防げる
- **上限の「月」は暦月ではなく請求期間**（契約開始日から次回更新日の前日まで）。
  暦月だと月末に入会した人が翌日に上限が復活してしまう
- **light の投稿が月2件なのは意図的**。1回目で投稿の仕方を覚え、**2回目で価値を実感する**。
  月1件だと一度うまくいかなかった時点で終わる

## 4. 逆算の論理 ★なぜこの設計なのか

pro から plus を逆算し、plus から light を逆算した。light から積み上げていない。

### pro を買う直前の心理は「満足」ではなく「喪失回避」

> **「こんな話ができる相手を、もう失いたくない」**

相手が匿名の「誰か」ではなく**固有名詞になっていて、その関係の終了が迫っている**状態。

### したがって各段はこうなる

| 段 | 必ず起こすこと | 絶対にやってはいけないこと | 卒業条件 |
|---|---|---|---|
| light | 自分の考えが変わる体験を**1回** | 固定メンバーとの継続対話を入れる／**単発で満足させ切る** | 「考えが変わった」が1回起きたら |
| plus | 相互に「また話したい」が成立／**終了日を設ける** | **1対1を出す**／「また話したい相手」を使い放題にする | 相互成立＋**本人が終了を惜しむ** |

**「終わりがないと、惜しむ感情が発生しない」**。plus に終了日がないと pro に上がる動機が生まれない。

**安いプランを「完成された小さな幸せ」にしない。** 満足させすぎると終着点になる。
「もっと深く話したい」という**未解決の熱を意図的に残す**のが階段の前提。

### 目標と転換率

**light 20人 / plus 10人 / pro 5人 / 月間アクティブ100人。**
各段の転換率50%。通常のファネル（5〜20%）とは桁が違う。

**n=20 はファネルではない。一人ずつ声をかける規模。** 個別の招待による50%転換は異常ではない。
そのために**会員一覧の管理画面**を作った（誰がどのプランか、次の段への合図が立っているか）。

**声をかける基準は非対称にする。**

| 段 | 基準 |
|---|---|
| light → plus | **合図1つ。**「考えが変わった」が立ったら |
| plus → pro | **2つ以上。うち「自分から募集した」か「人に届けた」が必須** |

受け身のまま月1万円へ誘うと、希少な創業者の時間を、まだ関係が固有化していない人に使うことになる。

## 5. 実装の構造

### 利用資格（エンタイトルメント）— `backend/entitlement.js`

**「この人はいま何ができるか」を1か所で決める。**

```
getEntitlement(uid) → guest / light / plus / pro
requirePlan(min)    → この段以上でないと通さないミドルウェア
consume(uid, kind)  → 上限を1つ使う。超えていたら false
usageOf(uid)        → いまの使用状況（画面に「あと◯件」を出す用）
```

**Stripe のプランを読むだけでは足りない。** 公式パス保有者には決済を通さずに
plus 相当を渡すため、`subscriptions` には何もない。
そこで**契約（Stripe）と付与（`entitlements/{uid}`）の両方を見て、上の段を採る**。

| 事故防止の設計 | 理由 |
|---|---|
| 支払い遅延（past_due）では締め出さない | Stripe が再試行中はまだ会員。1回の失敗で使えなくなるのは厳しすぎる |
| 契約が変わったらキャッシュを捨てる | 忘れると解約後もしばらく使えてしまう |
| 施行日より前は誰も止めない | 掲示した約束どおりにするため |
| 付与は「施行時に確定するレコード」 | 動的判定だと、基準日が変わったときに誰にいつ何を渡したか追えない |

### 止める場所は2つある

**Firestore ルールとサーバーの両方で止める。** 知識の投稿・募集・回答・議論は
**サーバーを通らずクライアントから直接 Firestore に書いている**ため、
ルールで止めないと**画面のボタンを隠すだけ**になる。

| 層 | 判定の正 |
|---|---|
| サーバーAPI | `requirePlan` / `consume` |
| Firestore への書き込み | Firestore ルールの `canWriteAs(rank)` |
| 画面 | **ボタンを隠すためだけ**（`window.emuEntitlement` は書き換えられる。セキュリティに使わない） |
| 契約の反映 | Stripe Webhook |
| 付与 | 運営（サーバー）だけが書けるレコード |

### 施行日の扱い

```
サーバー：ENFORCE_FROM = 2026-08-31T15:00:00Z （JST 9/1 0:00）
画面　　：EMU_ENFORCE_FROM = 同じ値
ルール　：timestamp.date(2026, 8, 31) + duration.value(15, 'h')
```

**ルールは `!enforcing() || myRank() >= minRank` と書いてあるため、
9/1まで左辺で短絡し、追加の読み取りが一切発生しない。** つまり施行日まで挙動は完全に今のまま。

### データの置き場

| コレクション | 用途 | 書ける人 |
|---|---|---|
| `subscriptions/{uid}` | Stripe 契約の写し | サーバーのみ |
| `entitlements/{uid}` | 付与（公式パス保有者・オーナー） | サーバーのみ |
| `plan_usage/{uid}_{期間}` | 請求期間ごとの使用回数 | サーバーのみ |

## 10. Stripe 本番切替の手順（商品完成後）

**いまテストモード。本物のカードは弾かれる。**

### 事故ポイント

秘密鍵と Webhook シークレットは独立した環境変数なので、**片方だけ本番になっても
コードはエラーを出さずに黙って動く。** 決済は成功するのに Webhook 検証だけ失敗し、
**「お金は取られたのに会員登録されない」**状態になる。

### 手順

1. Stripe を本番モードにし、light / plus / pro の商品と価格を作る
2. 本番用 Webhook（`https://emu-realtime.onrender.com/api/billing/webhook`）を作り、署名シークレットを控える
3. Render の環境変数**5つを1回の保存でまとめて**切り替える
   - `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` / `STRIPE_PRICE_LIGHT` / `STRIPE_PRICE_PLUS` / `STRIPE_PRICE_PRO`
4. **アクセスの少ない時間帯に実施**（保存すると再デプロイが走る）
5. 自分のカードで1件決済し、Webhook が届いて `subscriptions` が作られることを確認してから返金
