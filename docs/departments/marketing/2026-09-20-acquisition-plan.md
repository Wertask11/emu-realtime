## 1. 確定事項

### 1-1. 最上位KPIの現在地は「測定不能」

**Passport発行数の実数は取得できていない。**

- `ches_accounts` は `allow read: if signedIn()`（`firestore.rules` L505）。匿名REST GETは **403 PERMISSION_DENIED**（実測）
- `member_profiles` も同じく **403**。`posts` `sp_votes` は `allow read: if true` で **200**
- したがって「500〜1,000件に対して今何件か」は、**本セッションからは実数もレンジ推計も出せない**

> これが本プロジェクト最大の問題である。102日間、最上位KPIを測れないまま走ることになる。
> 経路選定より先に、ここを解くこと。

### 1-2. 媒体別の効果は「原理的に復元不可能」

権限の問題ではなく、**データモデルと運用の両方で記録されていない**。

- `ches_accounts` の保存フィールドは `uid, provider, displayName, email, photoURL, walletAddress, chesAddress, membership, tier, offchain, issuedAt, createdAt, lastLogin` のみ。**referrer / utm_source に相当する欄が存在しない**
- 8月の宣伝リンクは全媒体共通の素のURL（`https://schoolpark-emu.vercel.app/`）で **UTMなし**
- `provider` でログイン方法（LINE/Google/メール/ウォレット）の区別はできるが、これは「どの認証方式か」であって「どこを見て来たか」ではない

**KPI進捗の根拠として引用しないこと。** ファネル構造の説明に留める。

### 1-7. 実装上の制約（計測修復の前提として確認済み）

`firestore.rules` L506-509 の `ches_accounts` `allow create`：

- 検査しているのは `walletAddress is string` と `lastLoginBonusDate` キーの不在のみ
- **`hasOnly` による追加フィールドの禁止はない** → 流入元フィールドの追加に**ルール変更は不要**
- `allow update` は `changedOnly(['lastLogin','displayName','email','photoURL'])` 等に限定 → **一度書いた流入元は後から書き換えられない**（first-touchの改変防止として好都合。このままでよい）

## 2. 推奨案（未確定）

### 2-1.【最優先】計測を直す

102日を測定不能のまま走らないための最初の一手。

**(a) オーナーが今日できること（コード変更なし）**

1. **Firebase Console → Authentication → Users**。総ユーザー数が表示される。Passportは初回ログイン時にAuthアカウントと `ches_accounts` がほぼ同時に作られるため、**これが現状もっとも実数に近い代理指標**。プロバイダ列でLINE/Google/メール/ウォレットの内訳も目視できる
2. **Firebase Console → Firestore Database → `ches_accounts`**。コンソールのバージョンによってはクエリバーで COUNT が実行でき、件数が直接分かる
3. **1と2が大きくズレていたら、それ自体が重要な発見**（Authは作られたが `ches_accounts` の作成に失敗している等）
4. 各SNSのネイティブ分析を開き、8月投稿のインプレッション・プロフィールクリック数を確認する

**(b) UTM設計**

```
https://schoolpark-emu.vercel.app/?utm_source=<媒体>&utm_medium=<種別>&utm_campaign=<期間>&utm_content=<投稿単位>
```

| パラメータ | 値 |
|---|---|
| `utm_source` | x / instagram / tiktok / youtube / podcast / note / openchat / referral |
| `utm_medium` | social / video / audio / community / referral |
| `utm_campaign` | 週番号で固定運用（例 `2026w39`） |
| `utm_content` | 投稿単位の識別子 |

- **X**：1投稿=1リンクなので投稿単位まで付けられる。**最も細かい粒度が取れる唯一の媒体**
- **Instagram / TikTok**：プロフィールリンクは1本のみ。投稿単位は諦め `utm_content` を週単位に丸める。差し替えた日時を1行メモに残す
- **Podcast**：概要欄はエピソード単位で変更可能（`utm_content=ep1`）

**(c) `ches_accounts` への流入元保存（実装は技術開発部）**

- `_emuCreateAccountDoc()`（`index.html` L6746-6771）の `setDoc` に `signupUtmSource` / `signupUtmMedium` / `signupUtmCampaign` / `signupUtmContent` を追加
- 初回訪問時にURLクエリから読み、**`localStorage` 等の永続ストレージに保存**。クリックからログインまで数日空くため、セッションではなく**first-touchを残す設計**にする
- UTMが無い場合は `signupUtmSource: "direct"` を明示的に入れる（未設定とdirectを区別できないと集計できない）
- **Firestoreルールの変更は不要**（1-7参照）

**(d) GA4にログイン成立イベントを1つ追加**

`_emuCreateAccountDoc` 成功直後に `gtag('event', 'passport_issued', { method: provider })` を1行。これで「エンゲージメント → イベント」でログイン数が独立集計され、「集客 → トラフィック獲得」と掛け合わせて**媒体別ログイン数に最も近い数字**が取れる。

**(e) UTM導入までのGA4での代替範囲**

- レポート → 集客 → **トラフィック獲得**：参照元/メディア別のセッション数・ユーザー数
- レポート → ユーザー → **ユーザー獲得**：「最初のユーザーの参照元/メディア」で新規流入を媒体別に比較
- **代替できないもの**：ページを見ただけでは「ログインしたか」は分からない

### 2-2. オンライン経路の取捨選択

**先に警告：現状の延長では必要ペースに届かない。**

| | 週あたり |
|---|---|

| 全経路合計の見込み【推計】 | **10〜13件** |

**3〜5倍の不足。** 102日換算では145〜190件程度にしかならず、目標500〜1,000件に届かない。実データがない中の試算なので外れている可能性はあるが、**「今のやり方の延長で自然に届く」と楽観視できる根拠はない。**

| 経路 | 判定 | 週間見込み【推計】 | 手間 |
|---|---|---|---|
| X | **継続・最優先** | 約5〜6件 | 週1.5h |
| Instagram | 継続（週1〜2投稿に頻度を落とす） | 約2件 | 週1h |
| TikTok | 継続（週1〜2本） | 約2件弱 | 週1h |
| YouTube長尺 | **一時休止**（効果不明・工数重い） | — | — |
| YouTube Shorts | 継続可（TikTok素材の転用） | 0扱い（保守的） | ほぼ0 |
| Podcast | **一時休止**（音声はクリック導線が最弱） | — | — |
| note | 新規追加 | 1件未満 | 週0.5h |
| Web3オープンチャット | 新規追加（小さく） | 1件未満 | 週0.5h |
| リファラル（既存ユーザーへの声かけ） | 新規追加（初速ブースト、継続施策ではない） | 3〜4件（最初の2〜3週のみ） | ほぼ0 |

合計 **週4〜6時間**。対話キャパシティ（`emu-brand-strategy.md` §31）を圧迫しない範囲。

**推計の前提**（すべて仮置き。実測に置き換えること）

- X：週5投稿 × インプレッション500 × クリック率1.5% × ログイン率15% ≒ 5.6件
- Instagram：週2投稿 × リーチ800 × bio遷移率0.8% × 15% ≒ 1.9件
- TikTok：週1.5本 × 視聴1,500 × 遷移率0.5% × 15% ≒ 1.7件
- note：週1本 × 閲覧200 × 記事内遷移率3% × 15% ＝ 1件未満（記事は資産として蓄積し検索流入が後から増える可能性あり）
- Web3オープンチャット：1,000人 × 到達20% × 遷移2% × ログイン率20% ＝ 0.8件
- リファラル：行動する既存ユーザー5人 × 知人1.5人 × ログイン率50% ≒ 3.75件

**判断理由**

- **X最優先**：セグメント1（映画・本を語りたい層）と相性が良く、テキストのみで完結し、**投稿ごとにUTMを付けられる唯一の媒体**（次回検証の精度が最も上がる）
- **Podcast / YouTube長尺の休止**：収録12〜18分・撮影10〜15分という重い工数に対し、音声・長尺は計測もクリック導線も最弱。完全廃止ではなく「計測整備後に再開判断」
- **Web3オープンチャットの注意**：Emuのターゲットは「Web3・副業層」から「映画・本を深く語りたい層」へ転換済み。この経路ではEmu個別の訴求ではなく**SchoolPark／DAO全体の理念を主語にする**。EMUERの投資的表現は §32 により厳禁で、この経路が最も踏み外しやすい
- **リファラルの位置づけ**：継続エンジンではなく、母数13アドレスという小さな既存資産からの初速ブースト。既存のやり取りの中で一言添えるだけの設計

| 類型 | 規模感 | その場でログインする理由 | 決裁 | 見込み |
|---|---|---|---|---|
| ① 個人経営の学習塾 | 在籍20〜80人 | 自習室の入退室チェックイン、体験入塾の受付 | 塾長が即決 | 10〜40件 |

**声かけ文（A・学習塾／初回）**

**断られたとき（共通）**

> ご検討いただきありがとうございました。今すぐでなくても大丈夫です。もしご興味が出た際は、この案内を置いていただくだけで始められますので、いつでもお声がけください。

B・Cの文面も同じ構造（相手の業務 → 無料・決済不要 → 手間は案内を置くだけ）で用意済み。

**約束してよいこと**

- 設置物の用意と文面調整
- 見学・ログインが無料で決済情報が不要であること
- **先方から生徒・顧客の名簿を預かることはない**（本人が自分のスマホでログインする）
- トラブル時の窓口は創業者本人（対応速度は都度による）
- 設置物の月1回程度の差し替え

**約束してはいけないこと**

- 「集客が増える」「売上が上がる」といった断定的な効果保証
- 継続的な人員派遣・毎週のイベント開催・定期的な現地常駐
- 24時間対応や即時のトラブル解決
- 収益分配・紹介料・割引原資の確約（未設計）
- 会員同士の「マッチング」的な機能があるかのような説明（SchoolPark／Emuいずれにも現状その機能はない）
- 発行数のノルマ達成そのものを先方に約束すること

> **注意（レポート作成時に訂正）**：営業部の原案には「先方の顧客・生徒の個人情報をSchoolPark側が収集しない設計である」という説明項目があったが、`privacy.html` には氏名・メールアドレス・ウォレットアドレスの取得規定がある。提携先への説明としては事実と異なるため、上記のとおり**「先方から名簿を預かることはない」**という表現に修正した。

### 2-4. 下流KPIの見せ方

**ナレッジ103件を「量」として打ち出すことは推奨しない。**

- 投稿者13アドレス・69%が1アドレスという偏りは、外部から検証された場合に「多様なコミュニティ」という印象と食い違い、有利誤認に近い見え方になりうる
- 代わりに**個別の投稿・やり取りの中身（質）を見せる**。8/27投稿（「嫌なことをストレスなく乗り切るには」の実例）がすでにこの方針の良い前例
- 「103件」「13人」のような集計数字はそのまま外に出さない。**「立ち上げ期の少人数で、濃い対話が生まれている場所」**という誠実な表現に留める

**可決Proposal 0件・クエスト完走0件は「今は使わない」。**

隠すのでも、実績として打ち出すのでもない。今宣伝で使うと「0件」と正直に言うか嘘の実績を匂わせるかの二択になる。すでに8/19・8/30の投稿で「正直に話します」という誠実さをブランドの武器にしてきた実績があるため、**実際に1件でも可決・完走が出た時点で初めて語る**のが一貫している。
