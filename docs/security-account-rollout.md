# アカウント名義と集計の保護: 反映手順

## 変更

- アカウント名義をFirebase ID tokenからサーバーで確定する。一般ログインは既存と同じUID由来のCHESアドレス、ウォレットログインは署名確認済みのcustom tokenを使う。
- `ches_verified_accounts/{uid}` を新設し、Firestore Rulesの本人判定・運営判定はこのサーバー専用の記録を見る。旧来の自己申告アカウントは本人判定に使わない。
- `POST /api/auth/account` が既存プロフィールを保持して名義を検証・修復する。クライアントからのwalletAddress・chesAddressの作成や補完は拒否する。既存ウォレットの連携済みログインはサーバーの検証済み名義を再利用できる。
- 入場・ブランド選択は `POST /api/activity/entry` と `/api/activity/brand` を使う。名義と有料パス有無をサーバーで判断し、同一利用者・種別の短時間の重複を抑止する。同じ種別の60秒以内の再送は二重計上しない。未ログインのロゴタップは記録しない。
- ランキングAPIが検証済みの集計結果から先頭の利用者にバッジを付与する。クライアントからのバッジ・集計・入場履歴の書き込みは拒否する。公開表示に必要なバッジ・全体集計の読み取りは維持する。

## 本番への順番

Firebaseルールはユーザーが手動で公開する。先にルールだけを変更しない。

1. Renderにバックエンドを反映する。Vercelの自動反映と同時に行う場合は、フロントが先に切り替わらないようデプロイ順を制御する。
2. 認証なしで `POST https://emu-realtime.onrender.com/api/auth/account` が401 `AUTH_REQUIRED`を返すことを確認する。404なら旧版、503ならFirebase等の初期化に問題がある。
3. Vercelに新しいフロントを反映し、Google・メール・LINE・ウォレットの既存/新規ログインを確認する。自分のプロフィールが残り、CHESアドレスが付くこと、`ches_verified_accounts` がサーバーから作られることを確認する。
4. 新しいFirestoreルール全文を公開する。開いたままの旧フロントは再読み込みする。
5. 自分の下書き・投稿・リアクション・管理画面・ランキング・ブランド人数表示を確認する。既存の利用者も、新しいログイン処理または認証済みAPIの呼び出し時に検証済み記録が準備される。

旧自己申告アカウントしか持たない利用者は、検証済み名義が準備されるまで保護対象の操作を拒否される。既存ブラウザセッションで新フロントに更新できない場合は、再読み込みして必要なら再ログインする。

旧版への単純なコードロールバックは新ルールと互換ではない。新しい検証済み名義を作る処理を維持し、セキュリティ修正を巻き戻す形で包括許可を戻さない。

過去に不正登録・改ざんがあったかどうかは、この変更からは分からない。既存バッジ・集計を自動削除/再計算はしない。既存のウォレット連携・履歴の点検は別途必要。

## 検証

- バックエンドのHTTP/トランザクションテスト: Firebase token必須、bodyの名義無視、旧偽装アカウントの修復、署名済みウォレット/連携済みログイン、集計の二重送信、バッジ付与。
- Firestoreエミュレータ: 偽のアカウント・検証済み名義の作成禁止、名義補完の禁止、旧偽装記録からの他人の下書きアクセス禁止、正当な本人の下書き編集、バッジと集計への未認証/本人/運営ブラウザ書き込み禁止。
- フロント関数テスト: token付きのサーバー経由、同時要求の共有、アカウント切替時の応答拒否、サーバーの失敗通知。
- 本番の認証済み利用者によるログインや決済を、この開発環境のテストで実行したわけではない。
